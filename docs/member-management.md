# 階段三：會員管理與私人資料

2026-10-08 完成本機實作與測試；尚未部署，未修改正式會員資料。部署及正式站驗證仍由階段六追蹤。

## 管理流程

有效 Owner／Admin 在側欄可開啟「會員管理」，查看會員名稱、信箱、狀態、角色，並設定看板權限。

- 邀請：輸入名稱與 Google 信箱，選取角色與看板，建立 `pending` 會員及信箱索引。此功能不寄送電子郵件；管理員核准為 `active` 後，對方才能以該已驗證信箱登入。
- 核准／啟用、停用：修改會員狀態，不刪除歷史指派或留言。重新啟用保留既有會員 ID 與多信箱對應。
- Owner 可以管理所有角色與看板授權；Admin 只能管理非 Owner／Admin 的會員，且只能增減自己可存取的看板。Admin 表單保留其他看板的既有授權。
- 任何降級／停用都必須保留至少一位有效 Owner，並以交易處理同時修改的情況。
- 畫面保留儲存錯誤與表單。同一內容重試使用原請求識別碼；其他管理員已修改授權時拒絕覆寫，需重新載入。
- 登出、切換帳號或授權事件會關閉管理視窗並清空私人資料。延遲的名冊／儲存回應不會還原舊畫面。

`saveManagedMembership` 在同一 Firestore 交易中驗證操作者、目標原始授權、角色限制、看板存在性、信箱唯一性，寫入會員／索引及 `managementRequests` 收據。收據只保存操作種類、操作者、內容雜湊與結果，不存放明文邀請信箱。每次重試仍重新檢查管理員資格。同時邀請同一信箱只有一筆成功。

## 讀取範圍

原本有效會員可以列出整個 `members` 集合，因而取得其他會員的信箱與授權欄位。Firestore 規則無法只回傳文件中的部分欄位，現在採用可信任端點的欄位投影隔離顯示資料，無須搬遷或複製正式會員文件。

| 資料 | 允許讀取者 | 回傳範圍 |
| --- | --- | --- |
| `memberLookup/{email}` | 該已驗證信箱本人 | 自己的會員 ID |
| `members/{id}` | 有效會員本人 | 自己的會員資料；禁止列出集合，即使 Owner／Admin 也一樣 |
| `listDisplayMembers` | 有效會員 | 每位會員的 `id`、`name`，保留歷史作者名稱，不含信箱、狀態、角色或看板授權 |
| `listMembershipDirectory` | 有效 Owner／Admin | 管理所需的明確欄位：`id`、`name`、`emails`、`status`、`role`、`accessboard`；看板選項依操作者限制 |
| `managementRequests` | 可信任後端 | 客戶端不可讀寫 |

顯示名冊的「公開」僅指有效工作空間會員可見，未登入者、未核准或停用會員仍無法讀取。名稱唯一主資料仍在 `members`，本人仍可修改自己的名稱；多信箱會員不會產生重複名稱。名冊於登入／站內重新整理重新取得，沿用目前的名稱同步方式。

## 驗證紀錄

使用 Node 24、Java 21 與 `demo-rugatha-trello` 模擬器：

- `npm test`：86 項應用測試通過。
- `npm run test:rules`：33 項 Firestore 規則測試通過，包括本人限定讀取、禁止集合查詢與原有角色／撤權測試。
- `npm run test:management`：31 項 Auth＋Firestore＋Functions 整合測試通過，包括邀請、核准、停用、管理員越權、最後 Owner、衝突、重試與同信箱競態。
- Firefox：實際開啟 `http://127.0.0.1:8013/tests/browser/membership.html`，14 項介面測試通過。使用真實 `membership-ui.js` 與記憶體端點替身，涵蓋角色／看板設定、邀請／核准／停用、錯誤重試、HTML 字串安全顯示及撤權／延遲回應。補充測試發現並修復快速關閉再開啟時，舊 `close` 事件清空新視窗的競態。
- Firefox 主畫面冒煙檢查：未登入提示、建立／封存控制停用、會員管理入口隱藏均正常。

重跑瀏覽器測試：在專案根目錄啟動 `python3 -m http.server 8013 --bind 127.0.0.1`，以 Firefox 開啟上述測試頁，按「執行介面回歸測試」。測試頁不載入 Firebase SDK、不連接正式資料。

瀏覽器替身測試與模擬器整合測試分別驗證介面及後端，不代表已完成正式 Google 登入與已部署端點的端到端驗證。

## 階段六部署相依性

先部署管理 Functions（包含 `listDisplayMembers`、`listMembershipDirectory`、`saveManagedMembership`），再部署新版前端，最後收緊 Firestore 規則。若先收緊規則，舊前端的完整名冊查詢將被拒絕；若新前端先於顯示端點部署，登入將無法取得名冊並維持無權限狀態。部署期間需安排版本切換並要求舊分頁重新整理。

正式站待補驗：Owner／Admin 邀請及核准、受邀 Google 帳號登入、角色／看板變更與停用即時生效、一般會員不能取得他人的私人文件，以及多信箱名稱保持一致。
