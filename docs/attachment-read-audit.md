## 計費界線

依 [Firestore 官方計費說明](https://firebase.google.com/docs/firestore/pricing)，空查詢至少計一次文件讀取。上表的「文件回傳加空查詢」只用來估算這些直接查詢的最低文件讀取，不是專案帳單或 Firebase Usage 的計量值。

此量測使用管理登入，未走前端 Security Rules；排除安全規則的會員／lookup 相依讀取、身份／名冊載入、即時訂閱、SDK 快取、重連、交易及重試。量測程式另外讀取登入索引與會員共兩份文件。需透過 Firebase Usage／帳務匯出才能核對專案整體成本，且其中會混入其他使用者活動。

## 行為與驗證

- 封存清單補讀每批最多 10 個附件集合，只更新 UI 封存清單與已載入標記；不把延遲讀取結果寫入 Firestore。
- 有效附件陣列不因補讀被替換，避免影響正在使用的差異儲存基準。
- 載入失敗明確顯示錯誤，不顯示成「沒有附件」，關閉後重開可重試。
- 畫面關閉、帳號切換、看板重新載入後，舊請求結果不套用。
- 56 項應用測試通過，含零有效附件但存在封存附件、缺少計數舊資料、有附件牌卡、快取／失效與延遲回應競態。Firestore 規則未更動。
- Firefox localhost:8001 連接正式 Firebase：新版重新載入後，Viewer（viewer-test@example.com）與 Owner（owner-test@example.com）均可開啟 2027長團的封存清單（20 個延後查詢），顯示既有封存牌卡及無封存附件；Viewer 復原牌卡按鈕停用，Owner 可用。Viewer 關閉後重開正常。未實際復原或修改正式資料。
- 正式資料的零附件牌卡目前皆為空集合；「零有效附件但有封存附件」情境由回歸測試驗證。2026-10-10 新版已部署至 GitHub Pages，隔離牌卡的零附件封存／延遲查詢／復原及 Viewer 復原停用通過，見 [階段六驗證](phase6-live-verification.md)。

## 重跑

先在專案目錄以 Firebase CLI 登入可讀取正式專案的管理帳號，再執行：

```sh
node --experimental-vm-modules scripts/audit-firestore-reads.cjs 88eab0574749f210a394b6effadf36b2ad70cc36 > /tmp/attachment-read-audit.json
```

此命令會實際讀取正式資料，產生讀取用量。輸出僅有統計及看板名稱，不輸出憑證或卡片／附件內容。腳本不啟動訂閱，transaction 介面直接拒絕執行。

## 後續取捨

完整延後所有附件，需另外處理封面摘要、未載入附件的複製／儲存語意、卡片詳情載入與一致性。目前優先減去已確認的 340 次空查詢。若封存清單經常開啟，可再評估由可信任寫入流程維護封存附件計數或索引；直接使用有效附件計數無法證明不存在封存附件，不能因此永久跳過查詢。
